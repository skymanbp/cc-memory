最上游根因

projects.path——即解析后的 cwd 字串——在 v2.13.2 之前就是项目的身份，而每个表面都用自己的一套路径算术回答“这是哪个项目”：一边 resolve() 一边裸字串、normcase 却不 resolve、在所有平台上 .lower()、手拼状态目录名。同一个目录的两种拼写，就是两个身份。

ARCHITECTURE §7 早在 v2.6.0 就为根解析器写下了规则——“已存在的数据库就是身份声明”——但数据库内部那一行从未得到这条规则。这是 v2.13.0“状态目录名散落在 34 个 join 点”那个病的上一层：散落的不是目录的名字，而是项目的身份。

症状链：一个根因如何长出四层补丁

  1. 移动或重命名项目目录 → 记忆“消失”。core/db.py · upsert_project（协调者发现 M1，与 D3 同源）`upsert_project` 为新路径插入第二行 project；旧行的全部记忆、会话、进度行、计划、指令在每个表面失联。实测：移动后 SessionStart 注入 0 条记忆，list 打印 (none)，status 报告空库。
  2. 于是给每条查询加 WHERE project_id = ?（register E1），并让 CLI 打印“请手写 SQL 看旧行”。cli/mem.py · _require_project_id（register C4 注释）修的是串项目的症状，根因留在原地。
  3. status 却仍经 upsert_project 查行，rename 后自己造出第二行并报告空库，此后 stats/list/search 一律答 0 且无提示。cli/mem.py:770（D3）
  4. 合并标记为了活过 rename 长出路径检查；检查只 normcase 不 resolve，于是文档规定的 --project . 存成 "."，hook 永远视为外来，每次手动 /cc-mem consolidate 后都多跑一次后台 LLM 合并——正是 v2.12.0 共享写入器要防的那次冗余运行。core/consolidate.py:1094-1140 · cli/mem.py:1270（C1 / D2）· hooks/consolidate_async.py（C4 残留）
  5. 同一类拼写盲区散在别处：根解析器的 home 边界拿未解析的 $HOME 去比已解析的链，软链接 home 被走入并采用 home 目录下的库（A1）；仪表盘注册表在所有平台 .lower()，POSIX 上 Foo/foo 折叠成一条（E8）；/save-memories 自己拼 memory/，在已迁移到 .ccm/ 的项目里把每条记忆写进无人读的库（D1）。core/roots.py:212 · ui/dashboard.py:562 · skills/save-memories/SKILL.md:140

修在唯一的点上

  • core.layout.canonical_path / same_path / database_owner：全树唯一的“可比拼写”（先 resolve 再 normcase，永不抛错，非路径拼为空串只会 miss），以及“这个 memory.db 按位置属于谁”。modes._norm_path 改为委托，消掉第二份同样的降级序列。
  • MemoryDB.upsert_project：先精确匹配，再按 canonical 匹配；都不中且库正位于 <cwd>/.ccm/memory.db 时，把“最近活跃、且所记录目录已不存在”的那一行重新挂接到 cwd。所记录目录仍存在的行永不被拿走（即使是文件里唯一的一行——初版拿了，被 test_surfaces §9a 抓住）；不是 cwd 自己的库永不重新挂接。整个读-决-写在 BEGIN IMMEDIATE 里。
  • MemoryDB.find_project_id：提问类命令（status/stats/list/sessions/keywords）用的同一查找：会重新挂接，永不插入；库属于别的仍存在目录时如实报告。
  • 合并标记带 project_id，路径以解析后形式存储，回退比较两侧都走 canonical；两个读 marker 的 hook 传入 project_id。rename 不再付“多跑一次合并”的代价。
  • roots._home_dirs 同时收录每个 home 拼写的解析形式；DashboardApp._registry_key = canonical_path；save-memories 改问 core.layout.memory_dir。
