## Decisions I made

**Entry dicts stay two keys.** `tests/test_store.py:29` asserts exact equality against `[{"amount": 1.0, "note": "one"}]`, so the SQLite `id` column is an internal rowid that never surfaces in `entries()`, `add()`'s return, or the export. Insertion order is preserved via `ORDER BY id` — the JSON store's implicit list order was a real part of the contract (`cli list` numbers entries with it).

**No `close()` method, so connections are per-operation** (`store.py:67`). Adding `close()` would have extended the public interface you told me to freeze, and a long-lived handle would keep a lock on the DB file on Windows. Each call opens and closes a connection — a few hundred microseconds, irrelevant at this scale.

**Dropped the in-memory `_entries` cache.** The old store read the file once at construction, so two live `Store` objects on the same path silently diverged. Every read now hits SQLite, which makes `Store(path).add(...)` followed by `Store(path).total()` correct by construction rather than by luck.

**`total()` still sums in Python, not SQL.** `round(sum(...), 2)` over the rows gives float-for-float identical results to the old implementation; `SUM()` in SQLite would have been a silent numeric change for no benefit.

**Legacy JSON files migrate instead of crashing.** Pointing the new store at a file the old one wrote would otherwise raise `sqlite3.DatabaseError: file is not a database`. `_read_legacy_json()` (`store.py:76`) sniffs the SQLite magic bytes, and on a JSON file imports the entries and **renames** the original to `tally.json.legacy.json` rather than deleting it — verified above: 2 entries migrated, total 15.5, backup intact. Empty files are treated as fresh DBs.

**`add()` validates before writing** (`store.py:42`): `float(amount)` first, then reject `< 0`. Zero is still accepted — you specified negative. Bad types still raise `TypeError` from `float()` exactly as before.
